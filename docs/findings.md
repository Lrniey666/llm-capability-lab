# 發現

供應商型錄會列出一長串 ID。問題很單純：**裡面哪些真的具備它暗示的能力——例如看圖？**

下列數字來自存檔評測（刺激集 `menu_example/`，協議見 [vision-menu/protocol.md](vision-menu/protocol.md)）。方法可重跑；某一把金鑰當下看得到哪些 ID，會隨方案與時間改變。

三家（Gemini / Mistral / iAI）的 `GET /v1/models` 一共回了 **121 個型錄 ID**。
這不是 121 款對話模型：其中 **57 個是 TTS、embedding、繪圖等非 chat 端點**，探針直接略過。
其餘做了紅塊探針、或因配額中止（Groq 另見 [groq-eval.md](vision-menu/groq-eval.md)）：

| 結果 | 數量 | 意思 |
|---|---:|---|
| `accept_correct` | **12** | 收圖，而且答對 |
| **`accept_wrong`** | **9** | **收圖，但答錯——不報錯，就是錯** |
| `reject` | 12 | 明確拒絕（400／404），至少誠實 |
| `quota` | 29 | 額度用完 |
| `skipped_wrong_endpoint` | 57 | 型錄有、但不是 chat 端點 |
| `error` | 2 | 連線或伺服器端錯誤 |

那 9 個 `accept_wrong` 裡，**有 7 個是 `mistral-ocr-*`**——評測走的是它們自己的 `/v1/ocr`，
不是 Chat Completions。端點回 200，內容卻是財報表格這類**自信的錯誤內容**。
另外 2 個是 iAI 的 omni 模型，走 chat 吃了圖，回的是英文思考過程。

> **靜默失敗比拒絕更危險。**
> 回 `400` 的會叫你換端點；回錯答案的不會。
> 只看「呼叫有沒有成功」的系統，會把幻覺當成可用輸出。

視覺抽取用公開場景照片當刺激（**18 張台灣菜單圖**；核心四張跑完，擴充 14 張只跑到一部分）：
**224 次呼叫、218 次成功，但只有 99 次吐得出可解析的 JSON。**
核心集是 21 個通過探針的 ID × 4 張＝84 次。這就是本專案的論點：

> **JSON 解析成功 ≠ 內容正確。兩者必須分開量。**

評分是規則比對 gold 錨點，不是再拿一個 LLM 當裁判。

## 為什麼不用 LLM 當裁判？

用 LLM 評分 LLM 會把兩種錯誤混在一起：受測模型看錯了，還是裁判模型判錯了。
這組刺激有客觀對錯的欄位（品名／價格），這個不確定性沒必要引入。

所以評分改成規則比對：`gold.json` 標好高信心錨點，
用正規化後的字串比對與數值比對算召回率。代價是 gold 要人工標，
好處是**同一份資料重跑，分數必定一致**。

`gold_complete` 旗標另外解決一個問題：只有在該圖的 gold 標註是完整的時候，
多出來的項目才計為幻覺。半標註的圖不會因為模型多抓到真實內容而被扣分。

完整結果見 [最新報告](vision-menu/最新報告.md) 與 [gemini-mistral-iai-eval.md](vision-menu/gemini-mistral-iai-eval.md)。
